## Project

VELOUR — a premium fashion eCommerce site (men's & women's apparel, Zara/H&M-like
positioning, more upscale feel). Next.js (App Router) + TypeScript + React. No Tailwind — styling
is a single global stylesheet (`app/globals.css`) with CSS variables.

- Package manager: **npm**.
- Free-tier constraints: this project is meant to deploy for free on **Vercel's Hobby tier**.

## Backend (InsForge)

Real backend via [InsForge](https://insforge.dev) (project **velour**, linked in
`.insforge/project.json`; CLI: `npx @insforge/cli`). App code uses `@insforge/sdk`
through the single client in `lib/insforge.ts`; infrastructure (schema, RLS,
buckets) is managed via the CLI, not app code.

- **Tables** (all RLS-enabled; see `migrations/`):
  - `products` — public read-only catalogue. Seeded from the modest-wear catalog
    (see `lib/data.ts` BASE_PRODUCTS for the source content used at seed time).
    Columns are snake_case (`compare_at_price`, `is_new`); `lib/api.ts` maps rows
    to the camelCase `Product` shape.
  - `carts` — one row per (user_id, product_id, size); RLS restricts all access to
    `auth.uid() = user_id`.
  - `orders` — item/price snapshot in `items` jsonb; RLS allows insert/select for
    the owning user (`auth.uid() = user_id`), plus a narrow owner-only UPDATE
    (column-grant-restricted to `payment_status`/`status`, guarded by a trigger
    so the only client-side transition possible is
    `pending`+`unpaid` → `confirmed`+`paid`, exactly once — see
    `app/payment/`). `status` moves pending → confirmed → shipped → delivered;
    shipped/delivered transitions happen via the InsForge dashboard/DB, not the
    app. Payment is PayPal (PayPal.me link, `payment_status`/`payment_method`
    columns) — see `app/checkout/`, `app/payment/[orderId]/`,
    `app/payment/return/`. PayPal.me has no server callback, so payment
    confirmation is trust-based by design, not a bug.
- **Auth**: email + password via `insforge.auth`. Email verification is ON
  (`require_email_verification = true`, code-based) — signup shows a 6-digit
  code step before the account is usable. No *custom* SMTP provider is
  configured (`auth.smtp.enabled = false`), but verification codes still get
  delivered in practice — InsForge sends them from a default platform
  address (`noreply@insforge.dev`), confirmed by a real signup receiving and
  using a real code. Only throwaway/disposable test addresses (e.g.
  `@example.com` in automated testing) can't receive it, which is why test
  scripts in this repo mark `email_verified` via the CLI instead of waiting
  on a real inbox.
- **Storage buckets**: `product-images` (public — product photos) and
  `payment-uploads` (private — no longer used by app code; checkout's receipt
  upload was replaced by PayPal, bucket left in place rather than deleted).
- **RLS convention**: reference users with `auth.users(id)`; use `auth.uid()` in
  policies. Never bypass RLS from app code — infrastructure-level fixes (new
  tables/policies/buckets) go through the CLI (`db migrations`, `db query`,
  `storage create-bucket`), not the SDK.
- **Cross-component auth state**: no context provider was added; components that
  need to know sign-in state call `insforge.auth.getCurrentUser()` directly and
  listen for `lib/insforge.ts`'s `AUTH_CHANGED_EVENT` (dispatched by
  `notifyAuthChanged()` after sign-in/out) to re-check.

## Listings pipeline

- CSV: `incoming/listings.csv`, columns in order: `name, category, subcategory, price,
  compareAtPrice, description, sizes, image1, image2, featured, isNew, trending`.
- Images: flat folder at `incoming/images/`, filenames must match the CSV exactly (case-sensitive).
- Run `npm run import-listings` after any CSV/image change. It validates, optimizes images via
  `sharp` into `public/images/products/`, and regenerates `lib/generated-products.ts`. It's
  idempotent — safe to re-run.
- If rows are skipped or images are missing, fix the cause and re-run until clean; never silently
  drop a row without reporting it.

## Guardrails

- Don't redesign or restructure existing pages/components when asked to "wire in" something new
  (images, backend, payments) — connect to the existing seams (`lib/api.ts`, `lib/store.tsx`,
  the documented `PRODUCTS` line) rather than rebuilding.
- Keep `BASE_PRODUCTS` (demo data) in place even after switching to real products — just
  disconnect it via the documented line in `lib/data.ts`, don't delete it.
- Never hardcode secrets/API keys. Env vars go in `.env.local` (must stay git-ignored) and use the
  `NEXT_PUBLIC_` prefix only for values the client legitimately needs.
- Any task that touches money/payments/orders: keep amounts and status transitions server-verified
  where possible, and never fabricate a "paid" state without an actual confirmation step.

## Dependency isolation

- **Node/npm (primary):** All packages must be installed locally into the project
  (`npm install <pkg>`), never globally (`npm install -g`). This keeps `node_modules` scoped to
  the project and versions locked via `package-lock.json`. Never suggest or run global npm
  installs for project dependencies.
- **Python (only if any Python tooling is ever introduced — e.g. a one-off script):** Always use a
  virtual environment, never install into the system/global Python.
```bash
  python3 -m venv .venv
  source .venv/bin/activate
  pip install <package>
```
  Add `.venv/` to `.gitignore`. Never run `pip install` outside an activated venv, and never use
  `sudo pip install`.
- This project currently has **no Python dependencies** — it's a pure Node/Next.js stack. This
  section only applies if that changes later.
- Whatever the language, dependencies must be declared in the appropriate manifest
  (`package.json` for npm, `requirements.txt` for any future Python use) so the environment is
  reproducible from a clean clone.
